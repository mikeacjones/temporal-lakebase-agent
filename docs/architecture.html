01 · System topology

Three planes, one application

The architecture deliberately separates application compute, durable orchestration, and the governed data plane. Each can scale, roll out, and fail independently without collapsing the others into one hosting product.

Compute boundary

EKS runs the application

React/FastAPI and Temporal workers use different Kubernetes resources, images, replica policies, and scaling signals.

Control boundary

Temporal owns execution

Workflow history, retry policy, version routing, timers, and the human wait survive individual processes and pods.

Data boundary

Lakebase serves live state

Ordinary Postgres queries serve the UI and the agent while Unity Catalog governs inputs and consumes change history.

02 · Runtime behavior

Scale and release independently

User traffic is not worker demand. Splitting the web/API deployment from the Temporal Worker Controller-managed worker prevents a UI replica change from creating accidental poller capacity—and makes compatible worker rollout a first-class operation.

A Web / API tier

Two non-root replicas serve the built React application and FastAPI endpoints behind a private ClusterIP service.

  • Starts and signals Temporal workflows
  • Reads current run, transcript, review, and metrics views
  • Scales with browser and polling traffic

B Worker tier

A WorkerDeployment creates a Kubernetes Deployment for every active Temporal Worker Deployment Version.

  • Progressive rollout at 25%, 75%, and 99%
  • Per-version HPA from 1–10 replicas at 70% CPU
  • Per-version PDB keeps at least one replica available
  • Pinned compatibility keeps older workflows on a matching build
03 · Governed data loop

Policy comes down. Evidence goes back.

Lakebase is selected because the application sits inside a Databricks-governed data lifecycle—even though the process itself runs on EKS. A managed synced table serves governed Delta policy locally in Postgres; Lakebase CDF is the planned reverse path for operational audit history.

04 · Identity & trust

No database passwords in images

EKS workloads authenticate off-platform with a dedicated Databricks OAuth machine-to-machine service principal. The Databricks SDK resolves the endpoint and mints short-lived Lakebase credentials; TLS is mandatory and secrets enter pods only through secret injection.

Kubernetes

Secret injection

DATABRICKS_CLIENT_ID and DATABRICKS_CLIENT_SECRET come from the runtime Secret, never a Helm values file, ConfigMap, or image layer.

Temporal Cloud

Controller-owned connection

The controller references the Temporal API-key secret and injects address, namespace, deployment name, and build ID into versioned worker pods.

Databricks + Postgres

Two-layer least privilege

The service principal has Lakebase project CAN_USE only. Its matching Postgres role can read policy and read/write operational tables—without superuser, role creation, database creation, or schema administration.

Trust boundary: the setup/operator identity manages Unity Catalog, synced tables, and CDF. Runtime identities do not inherit those administrative capabilities. Separate web/API and worker identities are the recommended next hardening step.

05 · Failure & recovery

A dead worker is not lost work

Temporal history—not process memory—is the durable source of execution progress. Lakebase is the queryable operational projection. Killing a worker interrupts capacity, but it does not erase workflow history, completed tool results, or the pending human wait.

01

Execute

Workflow schedules credit and income activities.

02

Persist

Temporal records completion; Lakebase stores normalized evidence.

03

Hard kill

The worker receives SIGKILL—no cleanup or checkpoint hook.

04

Replay

A compatible worker resumes from event history and runs only remaining work.

05

Wait

The same execution reaches durable underwriter review.

The key separation: Temporal answers “what must happen next?” Lakebase answers “what should the application show now?” Rebuilding either concern inside the other would weaken the system.

06 · Hosting decision

Why this is not a Databricks App

Lakebase being the right database does not imply Databricks Apps is the right process runtime. Temporal workers need container-level scaling, concurrency tuning, graceful shutdown, version-aware rollout, and compatible old-build retention.

Compute near its scaling model. Data near its governance model.

EKS is the worker runtime. Temporal Cloud is the durable control plane. Databricks is the governed data plane.

Independent capacity

Worker pollers scale from queue workload and CPU; web replicas scale from HTTP demand.

Version-safe deployments

The Temporal Worker Controller creates a deployment per Worker Deployment Version and preserves pinned compatibility.

Operational control

Pod resources, probes, concurrency, HPA, PDB, shutdown grace, and rollout ramps are explicit Kubernetes configuration.

No loss of Lakebase value

Standard Postgres connectivity plus Databricks OAuth preserves low-latency access and the Unity Catalog data loop from EKS.
