What we built & why.

A production-shaped loan-underwriting agent where Temporal protects execution through failure and human delay, while Databricks Lakebase connects governed lakehouse policy to a low-latency operational application.

Temporal protects progress.
Lakebase closes the governed data loop.

Those are separate claims, implemented by separate layers, and demonstrated with separate evidence.

System shape

One application. Three clear planes.

Compute, durable orchestration, and governed data are deliberately decoupled. Databricks is the data plane—not the container runtime. The web/API and worker can scale, roll out, and fail independently on EKS.

↳
The critical boundary

No worker or web process runs as a Databricks App. EKS supplies containerized, independently tunable compute; Databricks supplies Lakebase and Unity Catalog.

Technology decisions

Why Temporal. Why Lakebase.

Neither product is used as a decorative dependency. Each solves a different failure mode in the end-to-end system.

Orchestration choice

Temporal makes progress durable.

Loan underwriting spans retries, external calls, process failure, and an unpredictable human wait. A normal queue plus database flags would recreate workflow semantics in application code.

  • Completed activities survive a hard worker failure.
  • Retries are policy-driven and observable, not hidden loops.
  • Signals resume the same deterministic execution after review.
  • Worker versioning keeps pinned workflows compatible during rollout.

Data platform choice

Lakebase closes the governed loop.

The UI needs ordinary indexed Postgres state, but the policy is governed in Unity Catalog and the reviewed outcome belongs back in Delta for audit and analytics.

  • Synced tables bring governed policy down to OLTP reads.
  • Standard Postgres serves the live run and review interface.
  • Databricks OAuth connects off-platform EKS workloads.
  • CDF can carry operational history back into Unity Catalog.

The fair comparison with Neon and other Postgres services

Neon is a credible serverless Postgres alternative with branching, autoscaling, scale-to-zero, and read replicas. Those database primitives are not the Lakebase claim. The differentiator here is who owns the two governed data paths around Postgres.

Capability used by this demoLakebaseNeon / external Postgres
Low-latency Postgres application stateNativeNative
Autoscaling, idle suspension, branchingNativeAvailable in Neon; varies by provider
Unity Catalog policy served as managed Postgres tableManaged synced tableSelect and operate replication or reverse ETL
Postgres changes written as Unity Catalog Delta historyLakebase CDF (Public Preview)Select and operate CDC or ETL
Durable retries, crash recovery, human waitTemporal—not the databaseTemporal—not the database

Decision boundary: if the application has no meaningful Databricks data gravity, compare providers on normal database criteria such as performance, regions, extensions, cost, and operations. Lakebase wins this demo because governed data must move from Unity Catalog into the app and reviewed evidence must move back—not because competitors are incapable Postgres platforms.

Least privilege

The runtime can operate the app. It cannot administer the platform.

The Kubernetes secret injects OAuth material at runtime; values are absent from source and Helm configuration. The Lakebase role has no superuser, database creation, role creation, or row-level-security bypass attributes.

  • Databricks project: CAN_USE only
  • agent_ops: schema use; table select/insert/update; sequence use
  • agent_policy: schema use; select one synced policy table
  • Explicitly absent: delete, schema creation, UC administration, project management, synced-table administration

Intentionally scoped

Safe demo defaults

  • The web service is private ClusterIP, reached by loopback port-forward.
  • A single dedicated runtime service principal minimizes demo credential surface; split API and worker identities for stronger production isolation.
  • The smoke workflow remains waiting so the live review path can be demonstrated.
  • Scripted model behavior keeps the proof repeatable; the activity boundary supports a configured model provider.

  • Production hardening may include identity split, network policy, alerting, SLOs, backups, and regional latency review.

Close the last mile

Three remaining actions.

The demo already proves the inbound policy path. These steps finish the human decision and outbound audit path without expanding the public attack surface.

1

Submit the waiting review

Use the documented loopback port-forward, open the deployed UI, and approve, deny, or request more information for the smoke run.

2

Enable Lakebase Change Data Feed

Map source schema agent_ops to agentworkflow_lakehouse.agent_ops from the production branch UI. CDF is a Public Preview feature and should be qualified accordingly.

3

Verify Delta change history

Confirm the pending row and completed review appear as insert, update preimage, and update postimage events in the generated lb_<table>_history tables.

Progress survives. Policy stays governed. Decisions stay visible.

That is the completed implementation thesis: Temporal and Lakebase solve different problems, and their boundary is what makes the system both durable and operationally useful.
