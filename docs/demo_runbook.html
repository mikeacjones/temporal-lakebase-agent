Prove the policy came from Unity Catalog

This is the first half of the Lakebase story: governed Delta data served locally through a managed synced table.

  1. Open Lakebase Postgres.

    In workspace dbc-33a81e40, open Lakebase Postgres → project temporal-lakebase-agentworkflow → branch production → SQL Editor.

  2. Select the database.

    Use databricks_postgres. The operational schema is agent_ops; the synced policy schema is agent_policy.

  3. Run the policy query.

    Read only: the synced target is managed and should not be updated directly.

Lakebase SQL · governed policyagent_policy
SELECT
    loan_purpose,
    min_credit_score,
    max_dti,
    decline_below_credit_score,
    decline_above_dti
FROM agent_policy.underwriting_policy_limits
WHERE loan_purpose = 'debt_consolidation';
ColumnExpectedMeaning
min_credit_score690Approval threshold
max_dti0.450045% approval threshold
decline_below_credit_score620Hard decline floor
decline_above_dti0.550055% hard decline ceiling
Why Lakebase“Neon, Aurora, or Supabase can be excellent Postgres backends. The reason for Lakebase here is not generic Postgres parity. Data engineering owns this policy in Unity Catalog, and a managed synced table serves it into operational Postgres without the agent querying an analytical warehouse or our team operating reverse ETL.”
Optional: verify all six governed rows

09

Enable CDF and close the governed loop

The decision leaves operational Postgres as append-only Delta change history in Unity Catalog.

Public Preview

Lakebase Change Data Feed is a Public Preview feature. State that openly. It is a schema-level feed, enabled in the Lakebase branch UI, and writes in roughly 15-second batches.

Enable the workspace preview

  1. Open workspace settings.

    Click your username in the Databricks top bar → Previews.

  2. Find Lakebase Change Data Feed.

    Enable it for the workspace. A workspace administrator may be required.

Start the feed on the production branch

  1. Open Lakebase Postgres.

    Project temporal-lakebase-agentworkflow → branch production → Change Data Feed.

  2. Click Start.

    Database: databricks_postgres. Source schema: agent_ops.

  3. Set the destination.

    Catalog: agentworkflow_lakehouse. Schema: agent_ops.

  4. Start and monitor.

    Use the Schemas and Tables tabs to confirm mapping, snapshot/streaming state, committed LSN, and last update.

Lakebase SQL · feed statuswal2delta
SELECT *
FROM wal2delta.tables
ORDER BY table_oid;

Expected: populated source tables progress through SNAPSHOTTING to STREAMING. Empty source tables are skipped until they receive a row.

Verify the review in Unity Catalog

After CDF is streaming and the review write exists, wait 15–30 seconds. Run this in Databricks SQL or Catalog Explorer:

Databricks SQL · outbound audit historyUnity Catalog Delta
SELECT
    run_id,
    review_id,
    reviewer_id,
    decision,
    rationale,
    decided_at,
    _pg_change_type,
    _pg_lsn,
    _timestamp
FROM agentworkflow_lakehouse.agent_ops.lb_agent_review_decisions_history
WHERE run_id = '37396a21-c6bd-4a0c-8a3a-96ce063609a8'
ORDER BY _pg_lsn;

Expected: an initial insert for the pending recommendation, then update_preimage and update_postimage rows when the human decision is recorded.

Close the Lakebase story“The policy came down from governed Delta into operational Postgres. The underwriter's decision is an ordinary Postgres update, and Lakebase CDF returns that change as Delta history for audit and analytics. With another Postgres provider we could build this, but we would own both data-movement seams. Lakebase makes both directions part of the Databricks platform.”

The review button is disabled or the API rejects the signal

Both Reviewer and Decision rationale are required. Refresh the run: the deterministic review ID changes if Request more info created a new review round. Only a run currently at awaiting_review accepts a review.

The policy source is not lakebase_synced_table

Stop and label the result honestly. Check the continuous synced-table resource temporal_agentworkflow_lakebase.agent_policy.underwriting_policy_limits and ensure it is online. The verified sync pipeline ID is ab876963-de71-49c4-b312-48debf8a2dc9.

The CDF history table does not exist

Confirm the workspace preview is enabled, the feed targets agentworkflow_lakehouse.agent_ops, and the source table contains a row. Empty sources are intentionally skipped. Check wal2delta.tables, wait for STREAMING, then allow another 15–30 seconds for the Delta batch.

Temporal and Lakebase appear briefly out of sync

Temporal is the execution system of record; Lakebase is the application read model. Activities write Lakebase and the UI polls it, so a short delay is normal immediately after a signal. Wait several seconds and refresh before diagnosing.

12

The 5-minute abbreviated path

Use this when the audience needs the thesis and proof, not an infrastructure tour.

Before the clock starts: have the port forward running, the UI on the waiting smoke run, the Lakebase SQL editor open, Temporal Cloud on the workflow, and Unity Catalog on the CDF history table.
  1. Frame the division of responsibility.

    “Temporal protects progress; Lakebase closes the governed data loop.” Point to the four tool results and pending review.

  2. Prove the inbound policy.

    Run the policy query: debt-consolidation thresholds are 690 credit and 45% DTI. Say that the source is a governed Unity Catalog Delta table served by a managed synced table.

  3. Prove durable execution.

    In Temporal Cloud, show the same workflow ID, completed activities, and durable wait. Skip the live worker kill unless it has been rehearsed.

  4. Approve the referral.

    In the UI, show credit 665, DTI 50.9%, and lakebase_synced_table. Enter reviewer and rationale, then Approve.

  5. Close the loop.

    Show the completed Lakebase review row and its update_postimage in lb_agent_review_decisions_history. End with the managed two-direction data-path comparison.

Final line“Temporal gives the agent durable, recoverable execution. Lakebase gives it operational Postgres without breaking the governed data loop: policy comes down from Unity Catalog, and reviewed decisions return as Delta history. Each product is doing the job it is built to do.”
